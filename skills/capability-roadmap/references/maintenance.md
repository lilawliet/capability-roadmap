# 持续维护：从代码区间到能力进度和发布安排

本流程服务于反复执行的进度同步。它规定输入、证据、更新边界和校验方式；业务判断仍由 Agent 与项目负责人完成，不是自动评审机器人，也不承诺分析百分之百正确。

## 选择本次模式

| 模式 | 适用条件 | 更新范围 |
| --- | --- | --- |
| 初始化 | 尚无能力目录、状态或稳定编号 | 建立需求基线、三层能力、证据与首版发布安排 |
| 增量同步 | 已有目录，提供新代码区间或需求变化 | 更新受影响能力，沿用未变化的编号与历史 |
| 结构迁移 | 已有 Markdown、表格或旧数据模型 | 保留既有事实与引用，建立编号映射和迁移校验 |
| 仅调整排期 | 能力目标与证据不变，只改变迭代顺序 | 修改阶段归属和发布切片，保留实现状态与复核时间 |

先识别项目已有的数据源、文档入口、生成方式和本地规则，复用既有工具。不要仅因调用此 Skill 就重建文档站、切换技术栈或搬迁数据。

## 固定代码和需求范围

将用户提供的分支或标签解析为完整 commit SHA，记录开始与结束节点、仓库、需求版本和本次范围。分支名会移动，不能作为唯一复核证据。若包含未提交改动，另行记录工作区差异，不能把它们算入结束 SHA。

在有本地提交对象时，可采用以下只读命令；将占位符替换为已解析的完整 SHA：

```sh
git rev-parse --verify '<开始引用>^{commit}'
git rev-parse --verify '<结束引用>^{commit}'
git merge-base --is-ancestor <开始SHA> <结束SHA>
git log --oneline <开始SHA>..<结束SHA>
git diff --name-status <开始SHA> <结束SHA>
git diff <开始SHA> <结束SHA> -- <相关路径>
```

`git log A..B` 是 B 可达而 A 不可达的提交集合；`git diff A B` 比较两个节点的最终文件树。两者配合识别意图与最终行为，不能把提交数量当成完成度。

若 A 不是 B 的祖先，先明确要回答的问题：

- 只比较两种当前实现：使用 `git diff A B`，指出其中包含两侧差异。
- 审查分支各自引入的变化：求共同祖先，分别审查共同祖先到 A、到 B，再核对两侧集成关系。
- 审查已完成的合并：核对合并节点的最终文件树，必要时检查各父节点；冲突解决可能产生任一父分支都没有的行为。

`git diff A...B` 只比较共同祖先到 B，不能代表 A、B 两侧的全部变化。不要盲用它而遗漏主分支变化。仅为分析差异，不擅自合并、变基或切换用户工作区。

远端引用无法刷新时，记录本地引用的 SHA 和获取限制；不要声称已经核对最新远端。多个仓库分别固定 SHA，不制造一个虚假的统一代码节点。

## 从变化定位能力

先读取上一轮总体范围与每个模块的独立复核时间。总体报告日期不等于全部模块已复核；某模块的证据可能早于上次报告。

1. 读取提交说明、差异和相关测试，提取行为变化、数据变化、约束变化。
2. 从入口追踪到调用链、持久化和外部依赖，理解变化在用户场景中的效果。
3. 将结果对应到现有业务、逻辑与数据、技术能力编号，形成待复核集合。
4. 检查横向影响：共享数据结构、鉴权、计费、缓存、配置、迁移、事件和公共组件可能影响多个模块。
5. 检查负向变化：删除入口、收紧权限、缺失回填、默认开关关闭、旧路径遗留，都可能改变可用性。
6. 对每个受影响模块更新证据和缺口，再检查阶段、发布切片与验收边界。

文件路径到能力编号是辅助索引，不是业务事实。一份文件可能服务多个能力；一个能力也可能跨越多个应用、服务和数据库。不要按目录机械分摊完成度。

对于核心共享依赖，不仅搜索直接调用；还要检查协议、数据约束和配置的间接消费者。证据不足时扩大只读检查范围，或明确保留未决事项。

## 保留历史判断，表达复核新鲜度

每个被重新评估的模块应能回答：本次按哪个需求目标、在哪个代码版本、看过什么、验证过什么、还缺什么、据此为何调整状态。

- 代码存在、测试通过、环境已部署、业务已验收是不同事实，分别记录。
- 没有查到代码不能直接认定“未实现”；记录已搜索范围和仍未知的部分。
- 未受影响且未复核的模块保留旧状态、旧证据和旧日期。
- 受影响但尚未完成复核的模块标为待复核或 stale，并保留旧证据；不要静默沿用为本轮结论。
- 状态不变也可能需要更新证据：例如修复边界条件，但尚未达到完整验收条件。
- 阻塞、降级和回归照实反映；不要为了让进度单向上升而隐藏退步。

新鲜度与实现状态是两个维度。展示“此前已实现，当前变更后待复核”比直接改成“未实现”更准确。数据结构尚不支持独立维度时，使用明确的复核说明并保留历史记录。

## 需求和编号演进

先版本化需求变化，再评价新范围。保留“旧需求已验收”的事实，将新增目标记录为后续增量；不能用扩大后的目标覆盖旧基线，让历史完成看起来从未成立。

识别需求来源是已确认决定、原型表达、分析推断还是待确认问题。新代码与旧需求矛盾时，记录差异并判断是否存在已授权变更；不要默认代码就是新需求。

稳定编号承担跨文档引用和历史追溯：

- 新能力追加新编号；调整名称或排序通常不更换编号。
- 拆分能力时，新建子能力编号并记录来源，明确原编号后续是聚合节点还是被替代节点。
- 合并能力时保留旧编号到新编号的映射，不让已有链接无声指向其他业务。
- 弃用能力保留弃用原因、替代项和历史引用；原编号不分配给不相关能力。
- 迁移完成前核对阶段归属、发布切片、依赖、证据、链接和个人试排数据的旧编号引用。

以项目现有版本策略保存变更记录即可；无需强制所有项目采用同一种文件结构或升级所有浏览器缓存。

## 持久化和视图依赖

小团队、文档随代码审阅的项目，优先复用 Git 中的结构化数据：可 diff、可审阅、可回退。使用数据库的合理动机包括多人在线编辑、权限控制、审计或已有项目管理系统；不要仅为“落库”而引入服务。

浏览器 localStorage 适合个人试排，不代表团队默认安排。需要团队共享时，应提供导入到正式数据的明确操作，或使用有审计能力的共享存储。数据库与 Git 并存时，指定权威来源与同步方向，避免双向静默覆盖。

能力树、阶段任务页、进度统计和路线图的能力状态共同引用稳定编号及同一事实数据。路线图引用能力的目标范围、复用关系和验收条件；实现状态变化不会自动替业务决定发布日期。

为可重复数据建立派生视图；说明文、历史总结、导出的静态图和演示文稿属于快照。记录快照的代码及数据基线，在能力数据变更时检查是否需要重生成。不能声称全部文档都已自动联动，除非实际实现并验证了该依赖。

当个人阶段试排与团队路线图不一致时，清楚展示差异。不要自动重写团队版本范围、依赖和承诺；把需重新确认的安排列入本轮交接。

## 校验和门禁按实际成熟度落实

优先运行项目已有的可执行检查。需要新增检查时，先确认真实数据结构与工具链，再实现、运行并记录结果；不要把文档中写下的建议说成已经接入 CI。

| 层级 | 可执行校验 | 能解决的问题 |
| --- | --- | --- |
| 数据完整性 | 唯一编号、合法状态、引用存在、需求及证据关联、依赖无环 | 损坏或悬空的数据关系 |
| 视图一致性 | 修改能力状态或阶段后，关联页、数量、链接一致变化 | 各页面维护了不同副本 |
| 发布语义 | 切片范围、验收条件、前置能力和完整交付归属可追溯 | 名称相同但交付含义不一致 |
| 文档构建 | 执行真实构建、链接检查，必要时检查可见页面 | 数据有效但页面无法使用 |

业务证据是否足够、需求是否正确，不能由编号校验替代。对状态提升和高影响变更，保留人工或独立 Agent 的抽查入口。

门禁可分阶段接入：先形成可运行命令，再加入项目检查脚本，最后接入合并或发布流程。按用户范围完成所选层级，并说明尚未接入的环节。只有实际执行成功，才报告检查通过。

不要为普通文案变化新增只检查固定措辞的测试。共享关联逻辑变更应验证可观察结果，例如阶段移动、弃用编号和未分配能力能否正确反映在派生页面。

## 每轮交接台账

使用项目现有文档或审计机制记录以下信息；无需为此强制新增数据库或固定 JSON 字段：

- 仓库与固定代码区间、祖先关系或共同祖先、需求版本、本轮模式。
- 受影响能力及影响原因、已复核集合、仍待复核集合、未覆盖范围。
- 状态变化和证据变化、需求增量、编号迁移与仍待决定的问题。
- 阶段及版本切片变化、依赖调整、需要人工确认的业务承诺。
- 实際执行的命令及结果、未执行检查、阻塞原因。
- 修改的权威数据和派生文档、代码／数据／文档各自的基线。
- 工作区完成、已提交、已推送、已构建、已发布分别处于什么状态。

提交、推送、创建 PR、发布文档站或生产环境，依照当前用户授权及项目规则执行。“更新进度文档”不自动授予全部后续外部操作的权限；已有明确授权可以沿用，无需重复询问。

## 可选接入项目规则

以下模板需按项目真实路径、命令和授权方式调整。是否写入项目 `AGENTS.md` 由用户选择；不要未经授权将方法论升级为全仓强制规则。

```markdown
### 能力进度与发布安排维护

影响用户能力、业务规则、共享数据或技术能力的变化，应检查能力目录中的对应编号及横向影响。
正式进度数据以 <权威数据位置> 为准；派生页面共同引用该数据，不各自维护状态副本。
增量同步记录完整代码 SHA、需求版本和每个已复核模块的证据；未复核模块保留旧基线。
需求扩展、编号迁移与发布切片分别记录，不用新目标覆盖历史验收事实。
完成同步后运行 <已存在且验证过的检查命令>；未覆盖范围和未执行检查必须说明。
提交及发布按本项目既有授权规则执行；个人试排设置不自动成为团队默认安排。
```

## 可复制的调用提示

**初始化：**“使用 capability-roadmap，结合此仓库当前代码和 <需求资料> 建立业务／逻辑与数据／技术能力三层目录、带证据的进度树，再按可验收的小版本形成发布路线图。沿用现有文档站，标清待确认项，不执行提交或发布。”

**增量：**“使用 capability-roadmap，审查 <开始 SHA> 到 <结束 SHA> 及 <需求变更>，同步既有能力进度、阶段页和发布路线图。先核对区间关系，保留未复核模块的旧基线，说明检查结果及未覆盖范围。提交和发布按本次明确授权执行。”

**仅排期：**“使用 capability-roadmap，基于现有能力数据和 <目标／期限／人力约束> 调整下一批小版本。保留实现状态与复核时间，说明切片验收、前置依赖和被推迟范围，不把计划调整写成开发进展。”

## 本轮完成标准

输入范围可复现；能力编号与需求目标可追溯；状态变化有行为证据；未知和待复核没有伪装成完成或未实现；所有关联视图读取一致事实；版本安排有可验收范围与明确依赖；检查、提交和发布状态按实际结果报告。

这套标准保证过程可检查、可接续和可纠正。后续提供代码区间时，Agent 仍须执行分析与验证，而不是仅将新提交摘要复制到进度树。
